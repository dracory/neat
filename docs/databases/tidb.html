TiDB

TiDB is a distributed SQL database with very high MySQL compatibility. It speaks the MySQL wire protocol and accepts the go-sql-driver/mysql driver, so Neat ORM's MySQL driver works with TiDB out of the box. The differences below are why a dedicated set of integration tests exists.

Connection

config := neat.DBConfig{
    Default: "tidb",
    Connections: map[string]neat.ConnectionConfig{
        "tidb": {
            Driver:   "mysql", // TiDB uses the MySQL driver
            Host:     "127.0.0.1",
            Port:     4000,
            Database: "test",
            Username: "root",
            Password: "",
            Charset:  "utf8mb4",
            Loc:      "Local",
        },
    },
}

Or via a DSN string:

dsn := "mysql://root:@tcp(127.0.0.1:4000)/test?charset=utf8mb4&parseTime=true&loc=Local"
db, err := neat.NewFromDSN(dsn)

Placeholder Format

TiDB uses the MySQL ? placeholder format, inherited from the MySQL driver.

Type Mappings

TiDB uses the MySQL grammar, so the MySQL type mappings table applies. The divergences listed below affect which types actually succeed at CREATE TABLE time.

Quirks and Divergences from MySQL

These are the documented differences that affect Neat ORM users. They are mirrored in the integration test suite under integration_tests/tidb/.

Quirk - Spatial types: TiDB has limited spatial type support. The schema builder generates a point column type that TiDB's parser rejects with Error 1064. The tidb_query_spatial_test.go integration test is skipped for this reason. See TiDB MySQL compatibility.

Quirk - Savepoints: TiDB does not support the SAVEPOINT syntax. Neat ORM's transaction layer emulates savepoints, which the TiDB transaction tests verify. Application code that calls Savepoint() / RollbackToSavepoint() works because the emulation handles the missing syntax.

Quirk - Shared locks: LOCK IN SHARE MODE is a no-op by default and requires tidb_enable_noop_functions=1 to be enabled. The tidb_query_lock_test.go shared-lock test is skipped for this reason. FOR UPDATE (used by LockForUpdate()) works normally.

Quirk - Foreign keys: TiDB v6.6+ supports foreign keys, but enforcement behavior may differ from MySQL. Test your specific constraint patterns before relying on them in production.

Quirk - Auto-increment: TiDB's AUTO_INCREMENT is not guaranteed to be sequential because IDs are allocated across the distributed cluster. Tests must not assert on sequential IDs - only on uniqueness and non-zero values.

Quirk - JSON: TiDB supports a subset of MySQL's JSON functions. JSON tests focus on basic store, retrieve, and query operations rather than the full MySQL JSON function set.

Quirk - Collation: TiDB defaults to utf8mb4_bin (case-sensitive), while MySQL 8 defaults to utf8mb4_0900_ai_ci (case-insensitive). Comparisons in WHERE clauses may return different results for the same data. Set the column or table collation explicitly if your application depends on case-insensitive matching.

Quirk - Isolation levels: TiDB does not support the SERIALIZABLE isolation level. Attempting to begin a transaction with sql.LevelSerializable returns Error 8048 (HY000): The isolation level 'SERIALIZABLE' is not supported. Setting tidb_skip_isolation_level_check=1 causes TiDB to silently downgrade SERIALIZABLE to REPEATABLE-READ. The tidb_transaction_test.go isolation-level test only covers ReadCommitted and RepeatableRead for this reason.

Behavior Notes

  • Distributed transactions: TiDB supports distributed transactions across nodes with snapshot isolation by default. Neat ORM's Transaction() API works as expected.
  • DDL: TiDB executes DDL online but some operations may take longer than on single-node MySQL because schema changes propagate across the cluster.
  • Concurrent access: LockForUpdate() blocks other transactions from acquiring the same row lock, as demonstrated in tidb_query_lock_test.go.

Default Ports

  • TiDB (MySQL protocol): 4000
  • TiDB status API: 10080
